# 织造排产离线验证

不启动界面即可批量验证排产与工时推演链路，失败时定位到具体工序/织机/依据。

## 运行

```bash
npm run verify
```

退出码：全部通过为 0，任一用例失败为 1。输出按套件列出每条用例的 ✓/✗，
失败时打印不一致的具体字段（工序、织机、档期、工时、顺延依据、裁决记录）。

## 结构

- `src/scheduling/types.ts` — 织机、订单、工序、能力、裁决与顺延依据的数据模型
- `src/scheduling/scheduler.ts` — 唯一推演核心：输入校验（依赖闭环/缺失依赖/指向缺失织机/能力覆盖不足）、
  织机裁决（优先级 + 织机编号决胜，全程留痕）、确定性仿真（同一输入必得同一结果）
- `src/scheduling/incremental.ts` — 变更应用与影响面分析（依赖闭包 + 同机台受影响后缀），
  只重推受影响工序，结果与整体重排一致
- `src/scheduling/entries.ts` — 三个触发入口（订单入口 / 织机看板入口 / 工序编辑入口），
  均为同一核心的投影，保证跨入口结论一致
- `verify/fixtures.ts` — 正常、边界、失败三类数据集
- `verify/diff.ts` — 两份排产结果的逐工序比对，产出可读差异行
- `verify/run.ts` — 套件运行器与报告

## 覆盖的验证面

1. 正常排布基准：基准数据集的档期、工时、顺延依据逐条断言
2. 入口一致性：同一数据从订单入口、织机看板入口、工序编辑入口触发，结论完全一致
3. 增量等价：改前置依赖 / 改织机能力后，只重推受影响工序，结果与整体重排一致，
   且受影响集合精确（未受影响工序不重推）
4. 裁决可追溯：多织机不同优先级覆盖时按优先级裁决并留存候选与规则；
   严格策略（`policy.strictAdjudication`）下直接判失败
5. 失败路径：依赖闭环（报告闭环路径）、依赖指向缺失工序、能力指向缺失织机、
   工序类型无织机覆盖

## 扩展

新增场景时在 `verify/fixtures.ts` 加数据集、在 `verify/run.ts` 对应套件加用例即可；
比对逻辑复用 `diffResults`，无需手写逐字段断言。
